# Audit général Smolcoder — 2026-10-10

Audit de terrain des trois interfaces (CLI/TUI, Web Hub, Electron), du cœur
agent/providers/outils et du dépôt. Rédigé après exécution réelle de la
compilation et de la suite de tests, pas seulement par lecture.

## 2. Problèmes critiques (corrigés)

### 2.1 Cycle de vie des processus Windows — CRITIQUE

- **Symptôme** : 2 tests rouges (`command cancellation…`, `task stop…`) et,
  surtout, des enfants de fond `cmd &` **jamais tués**. Ces orphelins gardaient
  ouverts les pipes hérités du processus lançant les tests → **`npm test` ne se
  terminait jamais** et des `node` zombies s'accumulaient (~500 Mo).
- **Cause** : `killTree` sur Windows ne faisait que
  `taskkill /pid <shell> /t /f`. Ici `taskkill` répond « Accès refusé » (logon
  restreint/sandbox) et, de toute façon, le shell était déjà sorti, donc son
  arbre n'était plus atteignable.
- **Correctif** (`src/tools/shell.ts`, `src/tools/tasks.ts`, `src/tools/index.ts`) :
  1. `killTree` termine d'abord **nativement** (`process.kill(pid, SIGKILL)`),
     ce qui marche même quand `taskkill` est refusé, puis tente `taskkill /T`.
  2. Le wrapper bash (`managedCommand`) **enregistre les PIDs Windows réels**
     des tâches de fond (`jobs -p` → `/proc/<pid>/winpid`) dans un fichier
     temporaire, que l'annulation / l'arrêt / le timeout vient terminer.
  3. Le token de suivi est propagé jusqu'au `TaskManager` (start + adopt).
- **Preuve** : les 2 tests passent en ~650-870 ms et la session CLI se termine
  proprement (exit 0) ; plus aucun fichier de suivi résiduel.

### 2.2 Étape 3.1 du plan (LSP) — terminée

- `queryCode` routait encore hover/def/refs/diag TypeScript vers le **client
  éphémère** (`src/lsp.ts`), soit un `npx typescript-language-server` froid par
  appel (~3 s) au lieu du manager persistant.
- Désormais **toutes** les actions passent par `src/lsp-pro.ts` (un serveur
  chaud par workspace). `src/lsp.ts` ne garde que les utilitaires protocolaires
  partagés ; son `querySymbols()` reste exporté pour les tests hérités.

### 2.3 Lock Cowork sous charge — stabilisé

- Fenêtre d'attente du lock portée de 15 s à 30 s (`src/tools/cowork.ts`) : 15 s
  provoquait de fausses erreurs « occupé » quand la suite complète saturait le
  CPU. Le test concurrent capture maintenant le `stderr` du worker pour un
  diagnostic immédiat en cas d'échec.

## 8. Socle « zéro régression » — CI et robustesse des tests (10-10-2026)

- **CI 3 OS enrichie** (`.github/workflows/test.yml`) : le workflow existant
  (ubuntu/macos/windows × node 22 + node 18 sur ubuntu, `npm ci` puis
  `npm test`) exécute désormais aussi `npm run qa` (typecheck + lint Biome +
  format Prettier), borné par `timeout-minutes` (10 pour QA, 50 pour la suite)
  avec remontée des journaux en artifact en cas d'échec, et un groupe de
  `concurrency` qui annule les runs obsolètes d'une même branche.
- **Filtre de tests** : `SMOLCODER_TEST_FILTER=a,b,c node scripts/test.cjs` ne
  lance que les fichiers de `test/` dont le nom contient un des motifs
  (insensible à la casse) ; un filtre sans correspondance sort en code 2. Sert
  aux boucles locales rapides et au découpage CI (ex. slice unitaire).
- **Cohérence de version** : `desktop/package.json` passe de `0.1.0` à `0.7.3`
  pour ne plus diverger de la version racine.
- **Flakys sous charge durcis** (deux tests d'intégration rouges uniquement
  pendant la suite complète, verts en isolation) :
  - `test/mcp.test.js` « slow server retry » : attente par sondage (jusqu'à 8 s)
    du retry d'arrière-plan au lieu d'un délai fixe de 1,4 s.
  - `test/offload.test.js` « detach » : borne de sortie du processus détaché
    portée de 10 s à 25 s (démarrage node + charge CPU de la suite).
